# OpenHands Memory Module

The Memory module in OpenHands is responsible for managing the agent's memory and context during conversations. It consists of two primary components:

1. **Memory Component**: Handles knowledge retrieval and context management
2. **Condenser Component**: Manages conversation history size by condensing events

## Technical Stack

- **Python 3.12+**: Core programming language
- **Pydantic**: For data modeling and validation
- **Asyncio**: For asynchronous operations
- **Event-driven Architecture**: Using EventStream for communication
- **Factory Pattern**: For creating condenser instances
- **Strategy Pattern**: For implementing different condensation strategies

## Memory Component

The Memory component serves as a knowledge retrieval system for the agent, providing:

- **Repository Information**: Details about the current repository
- **Runtime Information**: Information about the runtime environment
- **Microagent Knowledge**: Domain-specific knowledge from microagents
- **Conversation Instructions**: Specific instructions for the current conversation

### Microagent Types

- **RepoMicroagents**: Always active, provide repository-specific context
- **KnowledgeMicroagents**: Triggered by specific keywords, provide domain-specific knowledge

### Microagent Sources

- **Global Microagents**: Installed with OpenHands, available to all users
- **User Microagents**: Stored in ~/.openhands/microagents/, specific to the user
- **Workspace Microagents**: Found in the user's cloned repository (.openhands/microagents/)

## Condenser Component

The Condenser component is responsible for managing conversation history size by condensing events when necessary:

- Reduces the number of events included in the LLM context
- Summarizes or filters events to stay within token limits
- Maintains important context while removing less relevant information

### Condensation Process

1. When the context window or token limit is exceeded, the condenser starts condensing chunks of events into summaries
2. It summarizes the earlier events first, starting with the earliest agent actions and observations between two user messages
3. Then it processes later chunks of events between user messages
4. If there are no more agent events, it summarizes user messages individually if they're large enough and not immediately after an AgentFinishAction event
5. Summaries are generated by the LLM and saved in the State
6. Each summary is injected into the context in place of the events it summarizes

### Condenser Strategies

The module implements several condensation strategies:

- **LLMSummarizingCondenser**: Uses the LLM to generate summaries of forgotten events
- **AmortizedForgettingCondenser**: Gradually forgets older events
- **ConversationWindowCondenser**: Keeps a fixed window of recent events
- **BrowserOutputCondenser**: Specializes in condensing browser output
- **ObservationMaskingCondenser**: Masks certain parts of observations
- **NoOpCondenser**: Passes through events without condensation
- **RecentEventsCondenser**: Keeps only the most recent events
- **StructuredSummaryCondenser**: Creates structured summaries of events

## View Component

The View component represents a filtered and processed subset of the event history:

- Provides list-like access to the filtered events
- Handles the semantics of condensation events
- Ensures forgotten events are properly excluded
- Inserts summaries at the appropriate positions
